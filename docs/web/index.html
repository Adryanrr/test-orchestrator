Padrões de Projeto

Service Layer — API

Cada recurso da API possui uma classe que encapsula as chamadas HTTP. Os testes consomem essas classes via fixtures do pytest, sem fazer chamadas HTTP diretamente.

class PetService:
    def __init__(self, session: requests.Session, base_url: str) -> None:
        self._session = session
        self._base_url = base_url

    def create(self, payload: dict[str, object]) -> requests.Response:
        return self._session.post(f"{self._base_url}/pet", json=payload)

    def get(self, pet_id: int) -> requests.Response:
        return self._session.get(f"{self._base_url}/pet/{pet_id}")

Benefício: trocar requests por httpx exige mudança apenas na camada de serviços — testes permanecem intactos.

Page Object Model — Web

Cada página da aplicação SauceDemo é representada por uma classe que encapsula seletores e interações. O teste orquestra os Page Objects sem conhecer detalhes de implementação da UI.

class LoginPage:
    _username  = (By.ID, "user-name")
    _login_btn = (By.ID, "login-button")
    _error_msg = (By.CSS_SELECTOR, "[data-test='error']")

    def fill_credentials(self, username: str, password: str) -> None:
        self._wait.until(EC.visibility_of_element_located(
            self._username)).send_keys(username)

    def click_login(self) -> None:
        self._wait.until(EC.element_to_be_clickable(self._login_btn)).click()
        self._wait.until(EC.url_contains("inventory"))

    def get_error_message(self) -> str:
        return self._wait.until(EC.visibility_of_element_located(
            self._error_msg)).text

Benefício: seletor de um elemento muda em exatamente 1 lugar — nenhum teste precisa ser atualizado.

Testes negativos — validando erros da aplicação

Testes negativos verificam que a aplicação retorna erros corretos diante de entradas inválidas. Eles passam (PASSED) porque o sistema se comporta corretamente.

# API — recurso inexistente
def test_get_nonexistent_pet_returns_404(pet_service: PetService) -> None:
    response = pet_service.get(9_999_999_999)
    assert response.status_code == 404

# API — credenciais ausentes
def test_login_missing_credentials_returns_400(user_service) -> None:
    response = user_service.login("", "")
    assert response.status_code == 400

# Web — usuário bloqueado
def test_login_locked_user(driver):
    login = LoginPage(driver)
    login.open()
    login.fill_credentials("locked_out_user", "secret_sauce")
    login.attempt_login()
    assert "locked out" in login.get_error_message()

Erros & Soluções

Bugs reais encontrados durante o desenvolvimento e as soluções aplicadas.

Bug #1 — web/pages/checkout_page.py

Inputs React ignorados no Chrome headless (Linux/CI)

O Selenium nativo (send_keys) não dispara os eventos input/change que o React espera em inputs controlados. No headless do Linux o campo ficava vazio.

JS_SET_INPUT = """
var nativeSetter = Object.getOwnPropertyDescriptor(
    window.HTMLInputElement.prototype, 'value').set;
nativeSetter.call(arguments[0], arguments[1]);
arguments[0].dispatchEvent(new Event('input', { bubbles: true }));
arguments[0].dispatchEvent(new Event('change', { bubbles: true }));
"""
driver.execute_script(JS_SET_INPUT, element, value)
Bug #2 — web/pages/checkout_page.py

Botão Finish sem efeito com ActionChains

ActionChains simulava eventos sintetizados que o React ignorava. Substituído por clique via JavaScript direto no elemento.

driver.execute_script("arguments[0].click();", element)
Bug #3 — .github/workflows/ci.yml

Race condition no auto-merge do CI

Dois workflows paralelos (api-tests e web-tests) disputavam a criação do PR para developer. Solução: unificar em um pipeline único com concurrency group.

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true
Bug #4 — web/pages/ (todas as pages)

scrollIntoView quebrando interações no checkout

Chamadas de scrollIntoView antes de interagir com elementos criavam estado inconsistente nos componentes React. Removidas de todas as Page Objects.

Pipeline & Branches

Fluxo CI/CD

push / pull_request
       │
       ├── api-tests ─────────────────────────────────┐
       │   pytest api/tests/ -v                       │
       │   artefato: api-report.html + api-results.xml│
       │                                              ├─► auto-merge → developer
       └── web-tests ─────────────────────────────────┘   (apenas feature branches)
           pytest web/tests/ -v
           artefato: web-report.html + screenshot em falha

✅ Ambos passam → squash merge automático (gh pr merge --squash)
❌ Qualquer falha → branch bloqueada, sem merge
